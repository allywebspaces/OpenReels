# OpenReels autonomous continuation agreement

User authorization, 16 October 2026: take routine project decisions and carry work forward with minimal interruptions; obtain required credentials from the user. This extends routine implementation/delegation authority. It does not remove the existing English-only, free-first scope or authorize new spending/public posting. No guarantee of perfection or continuous execution is made.

## Concrete target

Prepare three original English micro-drama pilots for private review, with a reproducible free rendering path, evidence-backed output reviews and a clean developer handover. Complete this bounded milestone before creating channels or expanding to five topics. Channel naming remains provisional.

## Decisions the lead may take

Choose the next task, make reversible editorial/technical changes, use focused agents where supported, inspect/license-check useful repositories and relevant skills, install suitable free dependencies in an isolated environment, test, render within available free resources and commit verified work on experiment/video-quality. Avoid downloads on every turn: reuse existing tools unless an actual gap justifies another dependency. Preserve build/five-channel-starter and the approved MP4.

## Only escalate material blockers

Request a secure credential/login action when necessary. Never request secret values in chat, store them in the public repository or treat a key as permission to incur charges. New spending, public publication, account creation, external messages and destructive changes outside the agreed scope need explicit authorization. Subjective listening can remain explicitly unverified rather than being fabricated; continue independent work.

## How continuation works

An enabled task named **Advance OpenReels build** is configured with an hourly schedule in Asia/Kolkata. It resumes bounded work; it is not a continuously running worker. At configuration time no successful scheduled execution has been verified, and the scheduler did not return a next-run timestamp. Do not promise a particular first-run time or claim unattended completion from configuration alone. Each run depends on available tools, connections, permissions and account limits.

Web scheduled tasks do not preserve local folders/worktrees between runs. Fetch source/checkpoints from GitHub; restore a checkout when needed. If execution tools are unavailable, record the specific blocker and complete only work whose evidence is available. A GitHub edit is not proof of a render. Official reference: https://learn.chatgpt.com/docs/automations (web task source-persistence section).

Read PROJECT_STATE.json, ARCHITECTURE_HANDOVER.md, CURRENT_EPISODE_REVIEW.md and memory/INDEX.md. Perform one verifiable milestone, run appropriate checks, save evidence and commit. Compare the remote head before writing; use expected-head updates. On a lease conflict, reread and reconcile rather than overwrite another run. Do not retry an identical failure more than twice without new evidence. Keep commit/artifact links and scoped findings; do not dump the whole chat into every agent.

Notify only on a meaningful completed milestone or a new user-action blocker; suppress unchanged reminders. If a run cannot make progress, state why in the checkpoint rather than relabelling a proposal as implementation. The first scheduled execution is itself a validation milestone; inspect its actual result before declaring autopilot operational end to end.

## Acceptance and stopping conditions

1. Three original English pilots exist as independently decodable, accessible MP4 files, with scripts, source/render settings and hashes preserved in Git or another authorized persistent destination.
2. Each has inspected scene/key boundaries and a timestamped review; audio-listening limitations and any unresolved perceptual issues are explicit. No retention/earnings claim without measurements.
3. The first controlled alternative preserves the approved story/audio unless a separate change is recorded; baseline/candidate remain separately accessible.
4. Relevant software checks pass and free-mode language/source checks remain enforced. A clean setup/run recipe and known runtime blockers are documented; no hidden paid fallback.
5. Evidence for each acceptance item is linked in PROJECT_STATE.json. Then mark ready_for_review, stop feature expansion and pause the scheduled task if supported. If blocked on access/resources, save blocked status and a concrete user action instead of cycling endlessly.
